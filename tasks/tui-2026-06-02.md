# heartbit-tui — a terminal UI to chat with the framework (2026-06-02)

Goal: a credible equivalent of Claude Code / codex / opencode — an interactive TUI to
dialogue with the heartbit framework. Built as a new crate `crates/heartbit-tui`.

## Investigation (5-agent workflow wf_1cf25bb1-b88)

- **The bridge**: the chat REPL loop is INTERNAL to `AgentRunner::execute()` — when the
  LLM finishes without tool calls, `execute()` awaits the `on_input` callback for the next
  message (history preserved automatically). So the TUI runs ONE `execute()` in a
  background thread; callbacks bridge to channels.
- **Sync `OnApproval`** (`Fn(&[ToolCall]) -> ApprovalDecision`) is the load-bearing
  constraint: it must return from inside the agent future, so codex's single-`select!` loop
  doesn't transfer. Run the agent on a dedicated OS thread; bridge approval via a blocking
  `std::sync::mpsc` round-trip (agent thread idles waiting on the human).
- **No cancel token** → per-turn interrupt is impossible without cancelling the whole
  `execute()` (and losing history). v1: **Ctrl+C = quit**; per-turn interrupt deferred (needs
  a core change). Exclude the async question tool (would hang the agent thread unanswered).
- Reference: codex-rs/tui (Rust + ratatui) — actor/channel + imperative update + immediate
  -mode view; FrameRequester coalescing + `sync_update` for flicker-free; commit-animation
  for real-scrollback (deferred — v1 uses alt-screen + ratatui's double-buffer diffing).

## Architecture

- **Main thread**: async UI loop (`ratatui` draw + crossterm `EventStream`), owns the pure
  `App` state. All terminal/channel I/O here.
- **Dedicated agent thread**: `current_thread` tokio runtime `block_on`s `runner.execute()`.
  Sync callbacks (`on_text`/`on_event`/`on_approval`) send to the UI via a tokio mpsc;
  `on_input` (async) awaits a tokio mpsc fed by the UI (history automatic); `on_approval`
  blocks on a `std::sync::mpsc` reply. **Zero heartbit-core changes** — uses public seams.
- Provider from env (OpenRouter qwen preferred) via public API; `builtin_tools` rooted at cwd
  → a real coding agent. Layering on the public API also proves the framework is usable as a
  library.

## v1 credible feature set (the four non-negotiables, all met)
1. Flicker-free streaming (alt-screen + ratatui double-buffer + coalesced redraws + 120ms tick).
2. Tool-call cells: running (⏳) → ✓/✗ with timing + collapsed output.
3. Multi-turn that actually works (the `on_input` internal loop).
4. Terminal never corrupted: `ratatui::init` panic hook + `ratatui::restore` on every exit path.
Plus: approval modal (y/a/n) wired to sync `OnApproval` with a **Claude-Code-like permission
policy** (`default_permissions()`: read/grep/glob/list/todo → Allow silently; catch-all `*` →
Ask → write/edit/patch/bash prompt the modal; `[a]`lways persists as a learned rule); status

## Per-turn interrupt (added 2026-06-02 — the last "du même niveau" gap)
Core (heartbit-core): `agent/interrupt.rs` `InterruptHandle` — a **re-armable** wrapper over a
`tokio_util::sync::CancellationToken` (`interrupt()`/`is_interrupted()`/`token()`/`rearm()`),
re-exported at `heartbit_core::InterruptHandle`. `AgentRunnerBuilder::interrupt(handle)`. In
`execute_inner`, the LLM call is **raced** against the per-turn token (`Some(h) => select!{ biased;
cancelled => synth; r = llm_future => r } / None => llm_future.await`). On interrupt: synthesize a
clean `EndTurn` response (non-empty "[interrupted by user]" — providers reject empty assistant
content), `rearm()`, and let the EXISTING no-tool-calls path await the next `on_input` message — so
**history is preserved**. The cache write is guarded by `!interrupted`. `interrupt: None` is
byte-identical → zero regression (2673 core tests). Mid-tool abort is intentionally deferred: an Esc
during a tool is caught at the next LLM-call boundary (current tool batch completes first).
TUI: `Effect::Interrupt`; **Esc gated on `running`** (interrupts a turn; when idle just clears the
composer — so a stray Esc can't cancel the not-yet-started next turn); on interrupt the UI finalizes
the partial stream + a "interrupted" notice + goes idle. Verified live (pty): Esc mid-essay → "—
interrupted · ready", generation stopped, follow-up answered (session continued). 4 core + 2 TUI tests.

Known cosmetic seam (self-corrects): a few `on_text` deltas already queued when Esc fires can land
after the App finalized `active`, briefly re-creating a tiny fragment + flipping `running` true until
the synthetic `LlmDone` settles it. Cosmetic only; not fixed in v1.

## Mid-tool interrupt — SHIPPED + root-caused + live-verified (2026-06-02)
Esc during a running tool now abandons the batch in ~10ms, ends the turn, and returns to the prompt
(history preserved). Two real bugs were behind the earlier "reverted" attempt; a deep-research
workflow (4 agents + a 13-variant tokio bisection) found both:

1. **The shipped binary never raced the tool batch.** The earlier attempt was reverted, so
   `execute_tools_parallel` was a plain `.await` — there was no cancel arm to fire. The previous
   "live failure" was an *uninstrumented* observation across heavy add/revert churn, so it proved
   nothing about *where* the chain broke. The interrupt apparatus itself was always sound: the
   minimized cross-runtime repro (`interrupt.rs::cross_runtime_interrupt_aborts_subprocess_tool_race`)
   mirrors the exact live topology and passes; the bisection shows an *async* subprocess cancels at
   ~200ms on every runtime flavor (only a *blocking* call starves `current_thread`, and `bash.rs` is
   fully async). **Fix:** wrap the batch in `select!{ biased; cancelled => synthesize; r = execute => r }`
   (`runner.rs::execute_inner`); on cancel, synthesize an interrupted `ToolResult` + `ToolCallRecord`
   + emit `ToolCallCompleted` for EVERY allowed call (no orphan `tool_use`; the TUI ⏳ cell finalizes),
   leave the token cancelled so the next LLM-call race ends the turn. `synthesize_interrupted_tool_batch`
   helper. LSP/compression/reflection/summarization are guarded by `!tool_interrupted`. RED→GREEN:
   `runner::tests::interrupt_during_tool_batch_abandons_it_and_ends_turn` (RED 2.05s awaiting the
   sleep → GREEN 0.05s abandoning it).

2. **Killing bash orphaned its grandchildren** (a *pre-existing* bug the feature surfaced — the
   timeout path had it too). `bash -c` runs a compound statement (`cd … && { … }; …`), so it *forks*
   a `sleep` grandchild; `kill_on_drop` reaps only the bash leader, orphaning `sleep` (reparented to
   init, keeps running). **Fix (bash.rs):** spawn bash in its own process group (`process_group(0)`)
   and a `ProcessGroupKiller` RAII guard `kill(-pgid, SIGKILL)`s the whole tree on drop (timeout,
   error, OR interrupt-abort). Armed by default; **disarmed only on clean `Ok(Ok(output))`** so a
   recycled pid isn't killed and intentional `cmd &` background jobs survive (`bash_background_with_
   foreground` / `bash_trailing_ampersand` still green). RED→GREEN:
   `bash::tests::timed_out_command_kills_orphaned_grandchildren` (deterministic, via the timeout path).

**TUI:** the agent runtime is now `multi_thread(worker_threads=2)` (belt-and-suspenders so a future
*blocking* tool can't starve the cancel poll). Opt-in file diagnostics: `HEARTBIT_TUI_DEBUG=1` →
`/tmp/heartbit-tui-debug.log` (the TUI owns the terminal, so stderr is unusable); a `heartbit::interrupt`
tracing chain (CP1 TUI Effect → CP2 handle.interrupt() → CP4 batch race armed → CP3 cancel fired).

**Live proof (pty + real qwen, instrumented):** ask qwen to `sleep 20` via bash, approve, Esc ~2.5s
in. Log shows CP4→CP1→CP2→CP3 in order; `elapsed_esc_to_cp3 = 0.01s` (10ms abort), `sleep_running_
before_esc = True` → `sleep_running_after_abort = False` (the OS `sleep` is actually killed). Full
workspace gate green (fmt + clippy `--workspace --all-targets -D warnings` + `test --workspace`, 0 fail).

## Compact "aperçu" preview + auto-scroll-to-bottom fix (2026-06-02)
User report: a tool with long output (a web search) pushed the transcript BELOW the viewport and
the newest content vanished ("sous la ligne de flottaison"). Plus a product ask: "quand l'agent
travaille je ne veux voir qu'un aperçu de ce qu'il fait." Two compounding causes, both fixed
(research: workflow wf_47ecaaf2-3d1, 3 agents + ratatui-source review):

1. **Scroll counted LOGICAL lines, not VISUAL rows.** `ui.rs` computed the bottom-anchored offset
   from `lines.len()`, but `Wrap{trim:false}` makes a long line occupy several rows; the offset
   under-scrolled and clipped the newest content. **Fix:** count wrapped rows with
   `Paragraph::line_count(width)` (ratatui 0.29 feature `unstable-rendered-line-info`; it uses the
   SAME WordWrapper as the renderer, honours `trim:false`; the transcript has no block/border so the
   #1233 border caveat is moot). One-line change at the `total =` site. SOTA alternative (pre-wrap
   yourself + render without Wrap, à la codex-rs) is the documented upgrade path if borders are added.
   Test: `ui::tests::newest_content_stays_visible_when_earlier_lines_wrap` (TestBackend, RED→GREEN).

2. **Tool cells dumped output** (header + up to 12 NON-width-clamped lines → walls of wrapped text).
   User chose **"Compact"**: each tool = ONE line — `{marker} {name} ({ms})  {input summary}  → {output
   summary}`. `cells.rs`: `summarize_input` extracts the JSON value (command/query/path/url…) so it
   reads `seq 1 200`, not `{"command":"seq 1 200"}`; `output_summary` shows a short single line or
   `N lines`. The agent still SEES full output; the user sees only an aperçu. Tests:
   `completed_tool_renders_a_single_compact_line`, `compact_tool_input_summary_strips_json_wrapper`.

**Live proof (pty + real qwen):** "run `seq 1 200`" → rendered `✓ bash (11ms) seq 1 200 → 202 lines`
(one line, zero of the 200 numbers leaked), status `ready` + composer visible at the bottom (not
clipped). Full workspace gate green.

## MCP server support — connect any MCP server, tested with chrome-devtools (2026-06-03)
Goal: "on doit aussi avoir la possibilité de connecter un serveur MCP. Pour les tests on utilisera
chrome dev tools MCP." Live-verified end-to-end. heartbit-core already had the MCP client
(`McpClient::connect_stdio` / `connect_preset`); the work was exposing it through the TUI.

- **Config** (`tui.toml`): `mcp_servers: Vec<McpServerSpec>` — `{ preset = "chrome-devtools" }` or
  `{ command = "…", args = […] }` (TOML array-of-tables, `#[serde(default)]`).
- **`/mcp` command**: `/mcp [list]` · `/mcp add <preset>` (if in `known_presets()`) else
  `/mcp add <command> [args…]` (stdio) · `/mcp clear`. Persists via `Effect::SaveMcp`.
- **Auto-connect at startup (Claude-Code-style, 2026-06-03):** configured servers connect when the
  TUI starts — `spawn_agent()` is called eagerly at `run_ui` start (and the moment a key is set in-TUI)
  if a provider is available, so MCP tools are ready BEFORE the first message. The agent thread builds
  the runner (MCP connects → notices), then waits for the first user message on the same channel
  `on_input` uses (consumes it before `execute`), then runs. `SendInput` keeps spawn-if-not-started
  (so a session that ends via `RunCompleted` respawns + reconnects — the dead-channel fix survives).
  One spawn fn for all three triggers. Live-verified: with a server in config + a key, the
  `connected (26 tools)` notice appears at `0+0 tok` with ZERO messages sent.
- **Connection** (`build_runner`, now **async**): connect on the AGENT thread's runtime — the stdio
  transport binds to its spawn runtime, so connecting on the UI runtime would break tool calls. Order:
  **builtins FIRST, then MCP** (a server can't shadow a trusted builtin). Per-server Notice
  ("connecting…" → "connected (N tools)" / "failed: …"). `connect_mcp(spec)` dispatches preset vs stdio.
- **Threading refactor**: `build_runner` moved INTO the agent thread's `block_on` (build must follow
  MCP connect); `agent_started` set optimistically and reset on `RunCompleted` (only fires when the
  agent thread exits) — also fixes a latent bug where a dead agent thread left the UI sending to a dead
  `input_tx` forever.
- **Security**: `connect_stdio` inherits the process env (no `env_clear`) → an **exported**
  `OPENROUTER_API_KEY` is visible to spawned MCP servers; the **config-key path keeps the key out of
  the process env** (preferred). Documented residual (can't subtract from core's inherited env).

**Live proof (pty + qwen + real chrome-devtools MCP):** `/mcp add /usr/bin/chrome-devtools-mcp
--headless --isolated --executable-path /usr/bin/google-chrome`, then "open example.com + snapshot" →
`✓ new_page (768ms)`, `✓ take_snapshot (24ms)` (real MCP tools **executed and returned**) → agent
answered `…the page title is "Example Domain"` (the static page's title flowed back through the agent).
The preset `/mcp add chrome-devtools` (npx) uses the same `connect_stdio` core. Static page chosen
deliberately — a rAF/animated page never settles (chrome-devtools idle timeout). Full workspace gate
green; +5 unit tests (config roundtrip + 4 `/mcp` command tests).

## Markdown rendering (2026-06-03)
The assistant answers in Markdown, so `Cell::Agent` now renders it styled instead of showing raw
syntax. New `markdown.rs` (`render(text) -> Vec<Line>`, pure, pulldown-cmark): headings (bold + cyan,
`#` dropped), **bold** (BOLD), *italic* (ITALIC), ~~strike~~, `inline code` + fenced code blocks
(yellow, fences dropped), bullet/ordered lists (`•`/`N.` markers, nested indent), soft/hard breaks
preserved as line breaks, `---` rules; links/blockquotes degrade to their text. Wired at `cells.rs`
`Cell::Agent => markdown::render(text)` for the FINALIZED cell; the streaming `active` renders **plain**
(ui.rs `transcript_lines`) so partial markup never flashes styled mid-stream — Markdown is applied only
when the turn finalizes into history. (`ui::tests::streaming_renders_plain_finalized_renders_markdown`
locks both halves.) The renderer drops all raw markers — proven by
`markdown::tests::agent_pattern_strips_all_syntax` (heading+bold+italic+list+code → zero raw markers).
10 markdown unit tests + a `cells` styled-wiring test. Live: a real qwen Markdown answer rendered with
`•` bullets and code fences stripped (no `` ``` `` in the transcript). Perf note: parses per cell per
frame — fine now; cache per (content,width) if a long session lags.
